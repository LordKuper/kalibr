# Sprint 008-confirmed-levels-release-prep

## Goal
1. Нужно сделать так, чтобы подтверждённые по результатам комиссий уровни компетенций сохранялись и комиссия видела бы факт подтверждения на форме рассмотрения кандидата.
2. Нужно подготовить систему к первому релизу, зафиксировать API и структуру данных, включить режим миграции и обратной совместимости для будущих релизов. Для API обратная совместимость не нужна — будет только один консьюмер, наше же приложение в составе проекта.

## Acceptance

### Подтверждённые уровни

- AC-1: Подтверждённый уровень компетенции сотрудника — итоговый балл председателя по этой компетенции в заявке сотрудника со статусом «Решение вынесено», при любом решении, если сессия заявки дошла до этапа обратной связи (результаты опубликованы). Новая таблица не создаётся: значение вычисляется из итоговых баллов при чтении.
- AC-2: Карточка кандидата (`GET` и `PUT /api/v1/promotion/applications/{id}/review`) по каждой компетенции отдаёт последний подтверждённый уровень: балл, дату решения комиссии и целевой уровень той заявки; `null`, если подтверждений нет. Последний — с самой поздней датой решения. Рассматриваемая заявка своих баллов себе не подтверждает, даже когда её результаты опубликованы.
- AC-3: Формы председателя и члена комиссии показывают подтверждённый уровень в строке компетенции: балл, дату и целевой уровень. Без подтверждения строка выглядит как раньше. Более ранние подтверждения той же компетенции на форме не показываются.
- AC-4: Подтверждение действует по компетенции между версиями матриц: показывается у компетенции версии текущей заявки, если подтверждено в заявке по другой версии. Подтверждение компетенции, которой нет в версии текущей заявки, не показывается.
- AC-5: Откат сессии на этап до обратной связи снимает её подтверждения с формы, повторная публикация возвращает их с актуальными баллами. Заявка, которую откат вернул со статуса «Решение вынесено», подтверждений не даёт.
- AC-6: Подтверждение только информирует: рейтинг, готовность, начальный балл формы председателя, ранжирование и проверки не меняются.
- AC-7: Подтверждения получают только те, кто видит карточку кандидата: комиссия подразделения и администратор. Кандидат, оценивающие и ранжирование их не получают.
- AC-8: Демо-режим `/promotion/demo` и справка экранов показывают подтверждённый уровень на синтетических данных.

### Фиксация схемы и контракта

- AC-9: Все 15 миграций `src/Kalibr.Platform/Migrations/` удалены и заменены одной `InitialCreate` (удаление файлов разрешено пользователем). Она воспроизводит и то, чего нет в модели: расширение, функцию и триггеры журнала аудита, сопоставления, начальные данные. Схема и начальные данные чистой базы совпадают с результатом старой линии миграций; `ef-pending-changes` чист.
- AC-10: Все базы пересоздаются, данные не переносятся. `deploy/README.md` описывает это для единственного перехода на базовую миграцию; dev-базу пользователь пересоздаёт сам, агенты разрушающих команд Docker не выполняют.
- AC-11: Контракт зафиксирован: `ContractVersion` — 1.0.0, путь `/api/v1`, `openapi/openapi.json` и `web/src/api/schema.d.ts` актуальны (`check-api`).

### Режим миграций

- AC-12: В `.asd/project/config.yaml` `backward_compat: migration`; настройка меняется через `/asd-init` как объявленное в плане изменение.
- AC-13: Правило «No backward compatibility before 1.0» в `.asd/project/custom-common-rules.md` заменено правилом для релизов: обратной совместимости API нет — единственный потребитель, SPA, выходит вместе с API, устаревшее удаляется сразу, без deprecated и повышения версии контракта; схема БД меняется только вперёд, каждая миграция сохраняет данные и при необходимости переносит их; базовая миграция больше не пересоздаётся. Раздел «Контракт из кода» `docs/architecture/stack.html` и `docs/architecture/tech-reference/efcore-10.0.12.md` приведены к этому правилу.
- AC-14: `deploy/README.md` описывает обновление: резервная копия базы перед обновлением, откат — восстановление копии и прежний образ. Открытый вопрос Q5 (RPO/RTO и автоматическое резервное копирование) остаётся открытым.

### Права в БД

- AC-15: `app` в Kubernetes и dev-стеке подключается ролью без `SUPERUSER`, которая владеет базой; суперпользователь кластера — отдельная учётная запись, приложению не передаётся. Все миграции, включая расширение `pg_trgm`, и обычная работа проходят под этой ролью.
- AC-16: Интеграционные тесты запускают приложение под ролью без `SUPERUSER`; суперпользователем идут только проверки, которым он нужен по смыслу, например защита журнала аудита от `session_replication_role`.
- AC-17: Пункт «Учётная запись БД приложения» в `docs/architecture/stack.html` обновлён: прав суперпользователя нет, DDL из рантайма остаётся доступным и дальше ведётся как открытый; шаблон Secret и `deploy/README.md` описывают новые учётные записи.

### Оформление релиза

- AC-18: Версия приложения 1.0.0 задана в одном месте для всех проектов .NET, `web/package.json` несёт ту же версию, примеры `deploy/README.md` используют образ `kalibr-app:1.0.0`.
- AC-19: В корне репозитория есть `CHANGELOG.md` с разделом 1.0.0 и датой выпуска: что входит в первый релиз.
- AC-20: После мержа PR спринта на merge-коммит ставится аннотированный тег `v1.0.0`, он отправляется в `origin`; GitHub Release не создаётся.

## Out of scope
- Отдельная роль рантайма без DDL и миграции отдельным шагом развёртывания (варианты Г и В): в `stack.html` остаются открытыми.
- Поэтапные изменения схемы expand/contract: одна реплика и `strategy: Recreate`.
- Показ подтверждений кандидату, руководителю, в отчётах и на столе; история подтверждений на форме.
- Ввод или импорт подтверждений, полученных вне системы.
- Автоматизация резервного копирования, CSP, список браузеров, внутренний registry.
