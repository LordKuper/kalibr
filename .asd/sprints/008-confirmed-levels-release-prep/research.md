## Requirements
Raw scope and stage (a) answers; stage (c) refines the answers.
- Raw scope: (1) Нужно сделать так, чтобы подтверждённые по результатам комиссий уровни компетенций сохранялись и комиссия видела бы факт подтверждения на форме рассмотрения кандидата. (2) Нужно подготовить систему к первому релизу, зафиксировать API и структуру данных, включить режим миграции и обратной совместимости для будущих релизов. Для API обратная совместимость не нужна — будет только один консьюмер, наше же приложение в составе проекта.
- Problem: итоговые баллы председателя живут только внутри заявки; следующая комиссия не видит, какие уровни компетенций сотрудник уже подтвердил. До релиза проект работает без гарантий: миграции накоплены, схема и контракт меняются свободно, приложение ходит в БД суперпользователем, версии и истории выпусков нет.
- Actors: председатель и члены комиссии, администратор (видят форму кандидата); кандидат (чьи уровни подтверждаются); тот, кто разворачивает и обновляет систему.
- Functional requirements:
  - Подтверждённый уровень — итоговый балл председателя по компетенции в заявке, по которой комиссия вынесла решение, при любом решении.
  - На форме кандидата по каждой компетенции комиссия видит последний подтверждённый балл, дату подтверждения и целевой уровень той заявки; более ранние подтверждения на форме не показываются.
  - Базовая схема данных: все миграции сжаты в одну InitialCreate, включая изменения этого спринта; все базы пересоздаются, данных для переноса нет.
  - Контракт API 1.0.0 фиксируется как исходная точка; обратной совместимости API нет — единственный потребитель SPA выходит вместе с API.
  - Режим миграций для будущих релизов: `backward_compat` в настройках ASD и правила проекта для изменений схемы с сохранением данных.
  - Оформление релиза: версия 1.0.0 приложения и образа, CHANGELOG, git-тег v1.0.0.
  - Права в БД: приложение не работает суперпользователем кластера; остаётся единственной ролью и владельцем схемы, DDL из рантайма остаётся доступным, поэтому пункт `docs/architecture/stack.html` закрывается частично.
  - Момент подтверждения: наступление этапа обратной связи (публикация результатов), как у блока «Прошлые заявки»; откат сессии снимает подтверждение вместе с публикацией.
  - Гарантия режима миграций после релиза: только вперёд; каждая миграция сохраняет данные; перед обновлением делается резервная копия, откат — восстановление копии и прежний образ. Expand/contract не применяется: одна реплика, `strategy: Recreate`.
  - Контракт: версия 1.0.0 и путь `/api/v1` не меняются, снимок API закрепляет тег v1.0.0.
- Constraints: `custom-common-rules.md` «No financial data» и «No backward compatibility before 1.0» (правило заменяется этим спринтом); рейтинг считает только `ICareerModel.Score`; dev-базу пересоздаёт пользователь, агенты не выполняют разрушающие команды Docker; одна реплика `app`, `strategy: Recreate`, миграции при старте; образы собираются вне контура.
- Success criteria: при повторном рассмотрении кандидата комиссия видит подтверждённые баллы прошлых сессий; с нуля база поднимается одной миграцией и совпадает с моделью; будущая миграция проходит проверку на сохранность данных; приложение работает без прав суперпользователя; релиз 1.0.0 помечен в репозитории.

## Findings
- В EF Core нет встроенной команды сжатия миграций: обычный путь — удалить папку миграций и создать одну новую; объекты из сырого SQL (функции, триггеры), которых нет в модели, переносятся в новую базовую миграцию руками, иначе чистая база их не получит. У проекта это триггеры и функция журнала аудита. — source: https://codewithmukesh.com/blog/cleaning-migrations-efcore/
- Если базы не пересоздавать, новая базовая миграция считается невыполненной и падает на «already exists»; её надо вручную отмечать выполненной в `__EFMigrationsHistory`. Решение пользователя пересоздать все базы этот шаг снимает. — source: https://startdebugging.net/ru/2026/10/fix-there-is-already-an-object-named-in-the-database-after-resetting-ef-core-migrations/
- Microsoft рекомендует для production применять миграции SQL-скриптами или bundle, а не при старте приложения; идемпотентные скрипты сами пропускают уже применённые миграции; при нескольких экземплярах запуск при старте был опасен до EF 9. — source: https://learn.microsoft.com/ef/core/managing-schemas/migrations/applying
- Практика: `Database.Migrate()` при старте допустим только для одного экземпляра; провалившаяся миграция блокирует запуск. — source: https://milanjovanovic.tech/blog/ef-core-migrations-best-practices
- Приложению дают роль только с нужными правами на объекты, суперпользователь остаётся для обслуживания; случайный `DROP TABLE` такой ролью безопасно падает. — source: https://algomaster.io/learn/sql-interview/users-roles-privileges
- Владелец объектов — отдельная роль, миграции идут отдельной учётной записью; создатель таблицы становится её владельцем. — source: https://www.bytebase.com/blog/how-to-manage-postgres-users-and-roles
- Права на будущие таблицы выдаются группой ролей и `ALTER DEFAULT PRIVILEGES`. — source: https://oneuptime.com/blog/post/2026-01-21-postgresql-rbac/view
- `pg_trgm` — доверенное расширение PostgreSQL 13+: его создаёт не суперпользователь с правом CREATE на базу. — source: https://www.dbi-services.com/blog/postgresql-13-trusted-extensions/
- Expand/contract нужен, когда старая и новая версии кода работают с одной схемой одновременно: схема меняется поэтапно, откат обеспечивается этапами. У проекта одна реплика и `strategy: Recreate`, версии не пересекаются. — source: https://www.liquibase.com/technical-glossary/expand-contract-pattern
- HR-системы ведут историю уровня компетенции сотрудника: новая запись на каждое изменение, перезапись значения считается потерей истории. — source: https://docs.oracle.com/en/applications/jd-edwards/human-capital/9.2/eoahr/reviewing-competency-history-for-employees-1.html
- Модель оценки компетенций хранит только исходные оценки, производные значения считает, чтобы избежать расхождений. — source: https://arxiv.org/pdf/2001.09797
- Обычная запись первого выпуска в CHANGELOG — версия 1.0.0 с датой; выпуск помечается тегом с префиксом `v`. Первоисточники Keep a Changelog и SemVer поиском не получены, сведения из вторичного источника. — source: https://thecodeshastra.github.io/knowledge-base/docs/version_control_system/changelog

## Approaches
Два независимых решения: где живёт подтверждение (А, Б) и как запускаются миграции (В, Г, Д).
- **А. Вычислять подтверждение из итоговых баллов**: подтверждённый уровень — запрос к уже хранимым итоговым баллам заявок с решением; pros: нет дублирования; откат сессии и смена решения учитываются сами; меньше всего кода; таблицу можно добавить позже обычной миграцией с заполнением из тех же баллов; cons: подтверждение не отдельная запись, а правило чтения; живёт, пока живут заявки.
- **Б. Отдельный реестр подтверждений**: новая таблица-история «сотрудник, компетенция, балл, дата, заявка» пополняется при публикации результатов; pros: самостоятельная запись, готова для других экранов и отчётов и переживёт любую судьбу заявки; cons: дублирует итоговые баллы; откат сессии и смена решения требуют компенсирующих записей; больше кода и тестов.
- **В. Две роли БД, миграции отдельным шагом развёртывания**: перед стартом `app` тот же образ выполняет миграции под ролью-владельцем (init-контейнер), основной контейнер работает под ролью без DDL; pros: закрывает открытый пункт `stack.html` целиком; пароль владельца не попадает в работающий процесс; совпадает с рекомендацией Microsoft; cons: новый шаг развёртывания, новый режим запуска приложения, правки манифестов и инструкции.
- **Г. Две роли БД, миграции при старте приложения**: `app` получает две строки подключения, миграции идут первой, работа — второй; pros: развёртывание не меняется, правок меньше; cons: пароль владельца лежит в работающем процессе, изоляция слабее.
- **Д. Одна роль без прав суперпользователя**: приложение остаётся владельцем схемы, но перестаёт быть суперпользователем; pros: самая маленькая правка; cons: DDL, в том числе удаление триггеров журнала, остаётся доступным, пункт `stack.html` закрыт частично.
- Recommended: А + В — А не плодит второй источник правды, а добавление таблицы позже дёшево; В закрывает DDL-доступ из рантайма, а после заморозки схемы менять развёртывание дороже.
- Chosen: А + Д — выбор пользователя на стадии (c): подтверждение вычисляется из итоговых баллов; одна роль БД без прав суперпользователя, миграции при старте остаются (рекомендованное В отклонено).
